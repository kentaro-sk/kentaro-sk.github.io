# ポートフォリオ デザイン批評 × 改修提案（1ページずつ）

批評 → 統合 → 提案 → **ユーザーが採用案を選ぶ** → 実装、の順に進める。
サブエージェントは他のサブエージェントを起動できないため、進行はスキルを読んだ
メインの会話（あなた）が担う。**1回の実行で対象にするのは1ページ**（他ページの
共有クラス・見た目を巻き込まないため）。

## 全体の流れとゲート

```
[準備] → 1.批評(3体・並列) → 2.統合 → 3.提案(2〜4体・並列) → ★ゲート(採用案の決定) → 4.実装 → 5.検証 → 6.PR（マージは別途承認）
```

- **★ゲートを通るまで、コードは1行も変更しない。** 提案 → 確認 → 実装、の順序を守る。
- 中間成果物（批評・統合結果・提案）は**リポジトリ内に置かず**、スクラッチ領域に保存する。

## 手順

### 0. 準備
- 対象ページと、ユーザーの関心（例: 「文字の大きさが揃っていて見づらい」）を確認する。
- ローカル静的サーバ（例: `python -m http.server 8090`）を起動し、批評・提案の各エージェントが
  レンダリングできるURLを用意する。

### 1. 批評（並列）
- **1つのメッセージで**3体を同時に呼ぶ（Agent ツールを3回並べる）:
  `design-critic-minimalist` / `design-critic-apple` / `design-critic-google`。
- プロンプトには、対象URL・対象画面・ユーザーの関心を含める。各出力を保持する。

### 2. 統合
- `design-critique-summarizer` を呼び、**3体の出力をすべてプロンプトに含めて**渡す。
- 出力（総括・テーマ別・対立点・申し送り）を保存する。

### 3. 提案（並列）
- 統合結果の**論点に合うデザイナーを2〜4体**選び、1つのメッセージで同時に呼ぶ。
  全10体を毎回呼ぶ必要はない（コストに対して重複が増えるだけ）。

  | 論点 | 選ぶデザイナー |
  |---|---|
  | 文字の大きさ・階層・行間 | `designer-typography` |
  | 余白・情報密度・配置 | `designer-layout-whitespace` |
  | 配色・コントラスト | `designer-color` / `designer-accessibility-ux` |
  | 動き・hover | `designer-motion-interaction` |
  | 全体の思想（引き算・統一感） | `designer-muji` / `designer-apple` / `designer-google` |
  | 人となり・経歴の見せ方 | `designer-airbnb` / `designer-stripe` |

- プロンプトには**統合結果**（と必要ならユーザーの関心）を渡す。

### ★ゲート: 採用案の決定
- 各デザイナーの提案を並べ、共通点・対立点を整理し、**おすすめ案とその理由**を添えて
  ユーザーに提示する。採用する案（全部/一部/組み合わせ/却下）をユーザーが決めるのを待つ。
- ユーザーが独自の指示を追加した場合は、それを最優先にする。

### 4. 実装（承認後のみ）
- 採用された変更だけを実装する。次を守る:
  - 共有クラス（`.c-XXX`）を編集する前に、使用箇所を検索し、**他ページへの影響範囲**を確認する。
    1ページだけの調整はインライン指定を優先する。使われなくなったクラスは削除する。
  - `DESIGN.md` のトークン（サイズスケール・色・角丸・エレベーション）に従う。方針を変える場合は
    `DESIGN.md` も同時に更新する。
  - コメントは日本語で、理由まで書く。
- 秘密情報や、公開してはいけない固有名詞を書かない（フックが検知するが、意識して書く）。

### 5. 検証
- 実際にレンダリングして目視確認する（PC幅とスマホ幅）。スクロール連動の出現演出
  （`data-rv`）は完了まで待ってから撮影する（約2.5秒）。
- `npm run check:fast`（HTML・CSS構文）を実行する。必要に応じて
  `mobile-responsive-reviewer` / `pc-layout-reviewer` で崩れを確認する。

### 6. PR作成
- プロジェクトの CLAUDE.md の「Git 自動化ルール」に従い、コミット→push→PR作成→CI確認まで行う。
  **マージはしない**（マージ確認のフォーマットで承認を求める）。CIの警告は必ず報告する。

## 補足
- 検証は `portfolio-visual-check`（撮影・簡易検査）、共有クラスの編集前の確認は `refactoring-playbook` の
  「共有されているものを変える前に、使用箇所を調べる」、PR作成は `portfolio-pr-flow` に従う。
- サブエージェントの種類は Claude Code の**セッション開始時に**読み込まれる。見つからない場合は、
  `.claude/agents/<名前>.md` を読み込んだ `general-purpose` エージェントに、その定義を役割指示として
  渡して代替する。
- 決定事項（採用した案・見送った案とその理由）は、PRの説明文に書き残し、
  `DESIGN.md` に反映すべき内容があれば更新する。
