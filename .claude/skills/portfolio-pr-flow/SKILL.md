# PR 作成〜マージ確認の手順（ポートフォリオ）

このプロジェクトの Git 運用ルール（プロジェクトの CLAUDE.md「Git 自動化ルール」）を、手順として並べたもの。
**`main` へのマージ（＝本番反映）は、必ずユーザーの明示的な承認を得てから行う。** それ以外（ブランチ作成・
コミット・push・PR作成・CI確認）は確認なしで進めてよい。

## 1. ブランチを切る
- `main` への直接pushは禁止（保護ルール）。作業ブランチ名は `work/<日付>-<内容>`（kebab-case）。
- 作業ツリーに**無関係な未コミット変更**（別の作業のもの）がある場合、または現在のブランチが別作業のものの場合は、
  それを巻き込まないよう、`main` から別の作業ディレクトリを切る:
  ```
  git fetch origin
  git worktree add <ディレクトリ> -b work/<日付>-<内容> origin/main
  ```
  終わったら `git worktree remove` で片付ける。

## 2. コミットする前のチェック
- 変更が意図した範囲内か（`git diff` / `git status`）。無関係なファイルをステージしない（ファイルを指定して `git add`）。
- `npm run check:fast`（HTML・CSS構文）が通ること。
- 秘密情報・公開してはいけない固有名詞が入っていないこと（フックが検知するが、`git diff` を目視でも確認する）。
- コミットメッセージは日本語で `種別: 要約`（feat / fix / refactor / docs / test / chore）。

## 3. push して PR を作る
```
git push origin work/<日付>-<内容>
gh pr create --base main --title "種別: 要約" --body "<変更内容・補足>"
```
- PR説明には「何を・なぜ」と、決定事項（採用/見送りとその理由）を書く。

## 4. CIの結果を確認する（警告も必ず）
```
gh pr checks <PR番号> --watch          # 完了まで待つ
node scripts/ci-warnings.mjs <PR番号>  # 結論・失敗ステップ・警告のカテゴリ別一覧
```
- **警告は、ジョブが成功（緑）していても必ずユーザーに報告する**（画像サイズ・アクセシビリティ・Lighthouse・
  外部リンクの429・Node 20 廃止予告など）。黙って見なかったことにしない。
- **失敗した場合**は、原因を切り分けてから対応する:
  - 変更が原因（HTML/CSS構文エラー、内部リンク切れ、シークレット検出）→ 修正して再push。
  - 外部サイトへの接続失敗（`[0]`）と429は、リンクチェックが**警告扱い**にしているため、ジョブは失敗しない。
    `ci-warnings.mjs` の「リンクチェック」の警告として出るので、報告し、`curl` で実際に到達できるか確認する
    （恒常的に不通なら、リンク先の変更・廃止の可能性があるので修正を提案する）。
  - それ以外の一時的な外部要因でジョブが失敗した場合は、`gh run rerun <run-id> --failed` で失敗したジョブだけ再実行する。
    再実行しても失敗するなら、外部要因と決めつけず原因を調べる

## 5. マージ前の確認（必須。承認が出るまでマージしない）
次の形式でユーザーに提示する:

```
📋 マージ確認
　マージするブランチ: work/… → main
　PR: <タイトル> (#N) <URL>
　作業単位の内容: …
　CI結果: ✅ 必須チェック(check)は成功 / ⚠ 警告N件（下記）
　　- …
このままマージしてよいですか？
```
- 承認（「OK」「マージして」等）を得てから `gh pr merge <番号> --merge`。
- 次の操作は**マージ確認より重い扱い**で、個別にリスクを説明してから確認する: 強制push、`git reset --hard`、
  ファイル削除、保護ルールの変更、adminによるCIバイパスマージ。

## 6. マージ後
```
✅ マージ完了
　マージしたブランチ: work/… → main
　本番反映: https://kentaro-sk.github.io（数秒〜1分で反映）
```
- 作業用 worktree とローカルの作業ブランチを片付ける（別作業のブランチは触らない）。
- **リポジトリは常時 Public 運用**（2026-09-20〜。「作業後に Private へ戻す」暫定運用は撤回済み）。Private に戻さない。
  Private 化すると GitHub Pages の設定が削除され本番サイトが落ちるため、必要になったら実行前にユーザーへ確認する。
